## 1. Startup & topology

Process topology is in ARCHITECTURE.md §1; the web half in one paragraph: `StartWebApi()` runs on a fire-and-forget background task (`Program.cs:72`) inside the same process as the Discord bot. It builds a separate ASP.NET Core DI container and **bridges the Lamar singletons into it by instance** — `Global`, `GameReaction`, `CheckIfReady`, `GameUpdateMess`, `HelperFunctions`, `CharactersPull`, `CharacterPassives`, `Config`, `HttpClient`, `StartGameLogic`, `UserAccounts`, `DiscordWidgetService` (`Program.cs:100-111`) — so both frontends mutate the same live `GamesList` (`Global.cs:17`). Web-only singletons are registered on top: `WebGameService`, `GameNotificationService`, `GameStoryService`, `BlackjackService`, `BattleshipService`, `ReplayService` (`Program.cs:114-119`).

- JSON is camelCase for both SignalR (`Program.cs:122-127`) and controllers (`Program.cs:130-135`) — the TS interfaces in `signalr.ts` mirror C# DTOs 1:1 modulo casing.
- CORS default policy (`Program.cs:138-154`): origins `http://localhost:5173` (Vite), `http://localhost:3535`, `http://localhost`, `http://kotgh.ozvmusic.com`, `https://kotgh.ozvmusic.com`; any header/method + credentials.
- Middleware order (`Program.cs:156-200`): `UseDefaultFiles` → `UseStaticFiles` (wwwroot = built Vue SPA, `Program.cs:159-160`) → static `/art` from DataBase/art (`Program.cs:163-172`) → static `/sound` from DataBase/sound (`Program.cs:178-191`) → `UseRouting` → `UseCors` (`Program.cs:193-194`) → `MapControllers` (`Program.cs:196`) → `MapHub` at /gamehub (`Program.cs:197`) → SPA fallback `MapFallbackToFile` to `index.html` (`Program.cs:200`) — this fallback is what makes the client's history-mode routes work on refresh.
- Port: `KOTGH_PORT` env var, default 80, binds 0.0.0.0 (`Program.cs:202-204`). The env var is read **only** here; Config holds `Token`, `AnthropicApiKey`, and the default-off `GameStoryEnglishEnabled` switch (`Config.cs:9-29`, loaded from DataBase/config.json at `Config.cs:16`).
- In `--sim` mode neither Discord nor Kestrel starts (`Program.cs:61-70`); anything that needs a hub context (story push, notifications) simply never runs headless. The same block disables the Haiku service and replay capture (§9).
- Global web-relevant surface: `GamesList` (`Global.cs:17`), `FinishedGamesList` (`Global.cs:35`), and three callbacks — `OnGameFinished` (`Global.cs:41`) and `OnReplaySave` (`Global.cs:46`) registered by GameNotificationService, `SimErrorSink` for the sim harness (`Global.cs:52`). Game IDs are sequential via `GetNewtGamePlayingAndId` (`Global.cs:92-96`, note the "Newt" typo — it's load-bearing API).

## 2. Identity & auth — the trust model (Доверие)

**There is no password, token, cookie, or server-side session for normal play. The client asserts a Discord ID and the server trusts it.** Impersonation is possible by design (hobby-scale); the only OAuth-verified path is the profile widget (§12).

| Channel | Mechanism | Anchor |
|---|---|---|
| SignalR | client invokes `Authenticate(string discordIdStr)`; parsed ulong stored in `Context.Items["discordId"]`, connection registered | `GameHub.cs:61-78` |
| REST | `X-Discord-Id` header parsed per request; missing/unparseable → 401 | `GameController.cs:204-210` |
| Widget | Discord OAuth Bearer token verified against users/@me | `DiscordWidgetService.cs:116-143` |

IDs travel as **strings** over SignalR because Discord snowflakes exceed JS safe-integer range (`GameHub.cs:15-16`; string reply at `GameHub.cs:76`). On disconnect the connection is unregistered and the only "session" — the live connection's `Context.Items` — is gone (`GameHub.cs:45-53`).

**Account ID ranges** (routing in `UserAccounts.GetAccount`, `UserAccounts.cs:78-100`):

| Range | Kind | Created by |
|---|---|---|
| ≤ 1 000 000 | bot | `CreateBotAccount`, PlayerType 404 (`UserAccounts.cs:160-177`) |
| normal snowflakes | Discord human | `CreateUserAccount`, PlayerType 0, prefix `"*"` (`UserAccounts.cs:131-158`) |
| ≥ 9 000 000 000 000 000 000 | web-only | `CreateWebAccount` (`UserAccounts.cs:185-202`) via hub `RegisterWebAccount` (`GameHub.cs:147-173`): validates username 1-32 chars, allocates a monotonic ID (`GenerateWebUserId`, `UserAccounts.cs:204-210`; counter resumed past max existing web ID at startup, `UserAccounts.cs:37-46`), auto-authenticates the connection and replies `WebAccountCreated` |

`PlayerType` semantics: 0 Normal, 1 Casual, 2 Admin, 404 Bot (comment at `UserAccounts.cs:138`). Admin unlocks raw logs, full fight math, unmasked opponents (§7) and `CreateTestGame` (`GameHub.cs:510-535`).

**Persistence**: accounts live in a `ConcurrentDictionary` (`UserAccounts.cs:17`) loaded at construction — except under `--sim`, where `DisableDiskPersistence` starts the store empty and suppresses every write so parallel simulator processes cannot race or corrupt each other on the shared folder (ARCHITECTURE.md §10, finding M52); `IsPlaying` is force-reset for everyone at startup (`ClearPlayingStatus`, `UserAccounts.cs:61-65`). The guarded 60 s fallback flush and reward-critical writes both route through boolean `SaveAccount`, which locks the account across serialization/write and lets user-triggered transactions restore state when a write fails (`UserAccounts.cs:113-139`). Storage reports write success after replacing the canonical JSON through a unique same-directory temporary file; startup loads only `discordAccount-{numericId}.json`, ignoring temporary/backup artifacts (`UsersDataStorage.cs:28-80,83-116`).

Startup also runs the private unknown_bug account migration before normal use: legacy/current chance rows merge, every purchased hidden-weight change is refunded and the remaining internal row is reset to ×1.00; discovery is removed; statistics/mastery are merged under the new private key; history/last-played are renamed; any forced-next-character value is cleared; the two retired achievement IDs are purged from progress/notification queues. The account is immediately saved when any field changes (`UserAccounts.MigrateUnknownBugAccount`). Public stats/store/widget/auth DTOs still filter the migrated private rows.

## 6. Push model — who sends `GameState` when

1. **Per-action**: the hub pushes to the **acting player's connections only** right after each action (`PushStateToPlayer`, `GameHub.cs:1694-1702`).
2. **Timer**: GameNotificationService polls every 300 ms (`GameNotificationService.cs:97-103`) and broadcasts a game when the round number changed, elapsed time moved > 0.5 s, or any player's `IsReady` flipped (`PushUpdates`, `GameNotificationService.cs:218-269`; triggers at `GameNotificationService.cs:242-247`); a `RoundChanged` event accompanies round flips (`GameNotificationService.cs:258-261`). **Finished games are skipped by the timer** (`GameNotificationService.cs:236-240`) — their final state would race the lootbox/achievement stamping in the finish path.
3. **On finish**: the game loop fires `OnGameFinished`, which does the final personalized broadcast, emits `GameFinished`, conditionally kicks off story generation, and drops snapshots/room tracking (kept while a Blackjack table is still open) (`GameNotificationService.cs:78-96`). Active Madara `Вечное Цукуеми` and every unknown_bug roster skip the shared story because either artifact would cross a private-view boundary (`GameNotificationService` finish callback).
4. **Broadcast shape**: `BroadcastGameState` sends a **personalized DTO to every player with a web connection**, then one **spectator DTO** to the remaining connections in the room (`GameNotificationService.cs:178-208`). `SendGameStateToPlayer` is the single-player variant used by game logic (`GameNotificationService.cs:163-171`).
5. Replay saving rides the same finish path: `OnReplaySave` builds + persists the replay and appends its hash to each human's `ReplayHashes` (`GameNotificationService.cs:50-67`). Activated `Вечное Цукуеми` games never invoke that shared callback (`CheckIfReady.cs:850-858`); unknown_bug rosters are rejected again inside both the callback and `ReplayService` as defense in depth.

## 9. Replays

- **Round contract (format v2)**: `ReplayDataDto.ReplayFormatVersion = 2`; each logical `ReplayRoundDto` owns **PreFightPlayers** (the action-locked, per-viewer state before that round's fight calculation), the same round's deep-copied `FightLog`/global logs, and one authoritative post-setup `Players` result. The last round also has explicit personal/global settlement suffixes that exclude the already-captured round-11 setup buffer (`ReplayDto.cs:9-17`; shapes `ReplayDto.cs:45-76`; `ReplayService.cs:51-158`). Each player snapshot still contains that player's own full-visibility DTO plus the leaderboard exactly as that player saw it (`ReplayService.cs:329-371`).
- **Capture lifecycle**: `CalculateAllFights` clears the prior web fight log before `BeginRound` (`DoomsdayMachine.cs:187-224`); `CaptureRoundResult` freezes only combat/global logs before `RoundNo++` so Тигр bans, Darksci tilt and other next-turn messages cannot enter that stream (`DoomsdayMachine.cs:1662-1667`). After next-round effects and sorting, `FinalizeRound` remaps result players atomically, including only current **awarded bonus** score entries (not pending regular points for a never-played next round), so score/place/death/breakdown agree while action flags and combat stats still come from **PreFightPlayers** (`ReplayService.cs:74-116,329-371`; `DoomsdayMachine.cs:1936-1937`).
- **Game end**: `CaptureFinalState` refreshes the existing last combat result after final debits/predictions instead of adding a fake round 11. It subtracts per-player and global post-setup baselines and stores only `HandleLastRound` additions, preserving Geralt's pitchfork/winner/final-score logs without replaying round-11 Darksci tilt (`CheckIfReady.cs:845-853`; `ReplayService.cs:122-158`).
- **Finalize**: on game end `BuildReplayData` assembles `ReplayDataDto` (8-char `ReplayHash`, player summaries, max captured logical round, full chronicle) (`ReplayService.cs:162-213`), saved as camelCase JSON into the Replays folder (`ReplayService.cs:21,217-227`). Its inseparable final raw log buffer is retained for compatibility.
- **Madara privacy exception**: an active `Вечное Цукуеми` has six incompatible final views, so finalization/save is skipped rather than storing one viewer's projection or the authoritative ending (`CheckIfReady.cs:849-858`).
- **unknown_bug privacy exception**: no replay is persisted for a roster containing the private character. `BuildReplayData`/`SaveReplay` fail closed, and load/list/by-game-ID paths reject both current and legacy summary names, so already-existing files cannot re-enter anonymous or account replay surfaces (`GameNotificationService` replay callback; `ReplayService.ContainsPrivateRoster`).

- **Capture switch**: `ReplayService.CaptureEnabled` (`ReplayService.cs:36`) gates all per-round capture: with it off, `BeginRound` returns null — which short-circuits the round's remaining capture calls — and the final-state capture no-ops (`ReplayService.cs:51-158`). Production leaves it on; the headless simulator turns it off (`Program.cs:67`) because it neither saves nor serves replays, while capturing one costs a full six-player state projection — localization included — three times per round (finding M51).

## 14. Account-reward transaction boundary

All account-economy operations synchronize on the `DiscordAccountClass` instance: the finish path settles account/history/mastery/ZBS/quest/top-two-box/achievement/statistics together; Battleship, Daily Quest, loot, paid draft picks and both Discord/web stores use that same account monitor (`CheckIfReady.cs:744-818`; `BattleshipService.cs:35-119`; `QuestClass.cs:358-508,638-723`; web store `WebGameService.cs:1209-1422`; Discord store `StoreReactions.cs:160-549`). This prevents simultaneous reward, reroll, pick or shop actions from losing a balance/box/progress update.

Daily Quest day/week initialization is a durable user-visible mutation: `RequestQuests` snapshots the complete quest/economy state, normalizes/migrates with one UTC timestamp, saves before sending, and restores on failure. `RerollDailyQuest` uses the same contract, including replacement progress and any immediately earned card/daily/mastery/weekly rewards (`QuestClass.cs:283-355,414-508`; `GameHub.cs:675-742`). Game-end progress uses the ordinary settlement policy: retain the completed in-memory transaction for periodic retry if the immediate save fails. Full semantics: [DAILY-QUESTS.md](DAILY-QUESTS.md).

Loot results are retry-safe rather than client-animated randomness. `QuestData.LastLootBox` persists the last `OpeningId`; until acknowledged, every V2 open returns it without another debit/credit. `RequestQuests` returns that unacknowledged record with current account totals and the guaranteed-character queue head/count for reload/reconnect recovery (`GameHub.cs:675-710`). `OpenLootBoxV2` snapshots and restores ZBS, inventory, pity/result state, `CharacterChance`, `SeenCharacters` and `LootBoxCharacterQueue` around the save; acknowledgement retains the same durable boundary. Legacy `OpenLootBox` acknowledges inside the transaction so cached clients without the new acknowledgement call do not become stuck (`QuestService.OpenLootBox`, `QuestClass.cs:842-997`; `OpenLootBoxCore`/`CaptureLootBoxAccountState`, `GameHub.cs:839-940`, `GameHub.cs:1664-1715`). The reveal animation never determines any reward.

New results use `SecureRandom`: reward amounts use its inclusive bounds and rarity rolls use 10,000 equally likely outcomes with cumulative cutoffs 50/300/1500/4000, exactly preserving the published 0.5/2.5/12/25/60% base distribution (`QuestService.RollLootBoxTier`; RNG implementation `SecureRandom.cs:17-25`). The selected public character is another secure draw; Epic limits it to Tier 1–2 and Legendary to Tier 1. Pity upgrades only a tenth consecutive below-Rare natural result; the upgraded result receives the complete Rare ZBS/+3 character package and does not replace a natural Rare+.

User-triggered economy writes are durable before confirmation: Daily Quest, loot, achievement acknowledgement, paid draft, and both store transaction paths save while holding the account monitor, then restore their exact in-memory snapshot before returning a retryable error if replacement fails (web store `WebGameService.cs:1234-1379`; Discord store `StoreReactions.cs:160-549`). `SaveAccount` reports the atomic-replace result (`UserAccounts.cs:113-139`; `UsersDataStorage.cs:28-80`). A real-player game-end save failure is critical-logged and retains its settled in-memory state for the periodic retry; bot accounts deliberately skip the immediate disk write (`CheckIfReady.cs:812-818`).

Achievement V2 generally filters unknown legacy IDs rather than inferring retroactive rewards from match history (`AchievementClass.cs` catalog/board filtering; `GameHub.cs` achievement board). The two retired private-character IDs are the explicit cleanup exception: startup removes their stale progress and acknowledgement entries without clawing back already-issued rewards (`UserAccounts.MigrateUnknownBugAccount`). Daily Quest V1 instead has an explicit same-day economy migration: paid legacy days become settled without a second payout; unpaid days begin V2, while loot state is preserved (`QuestClass.cs:283-355,734-797`).

## 15. Known quirks & pitfalls (backend)

- **Asserted-ID auth**: any client can claim any Discord ID (§2). Never build features assuming web identity is verified; the only verified flag is `WidgetAuthorized` (`DiscordWidgetService.cs:141`).
- **REST is a subset** — new player-facing actions must be added to the hub (and usually only the hub); adding them to GameController is optional parity.
- **ARAM has hub/REST methods but no web UI** — AramReroll/AramConfirm are callable and the reroll counters are serialized, but the Vue client never renders an ARAM pick screen (finding **m24** in AUDIT-FINDINGS.md; WEB-CLIENT.md §13).
- `Attack` pushes state even when rejected (`GameHub.cs:228-235`) — the client relies on this to re-sync after refusals; other actions push on success only.
- Finished games are invisible to the 300 ms timer (§6) — if you add finish-time data to the DTO, populate it **before** the finish callback fires or it will never reach clients.
- New per-player web state needs the whole §7 pipeline: DTO member (`GameStateDto.cs`), mapper case with the right isMe/isAdmin gate (`GameStateMapper.cs`), TS mirror + widget (ARCHITECTURE.md §7 steps 11-14). Missing the gate = information leak to opponents/spectators.
- `KOTGH_PORT` is env-only (`Program.cs:202`); Config carries the bot token, Anthropic key, and default-off `GameStoryEnglishEnabled` switch (`Config.cs:9-29`).
- Discord IDs cross the hub as strings; the server parses with `ulong.TryParse` (`GameHub.cs:69-74`) — never let the client send them as JS numbers.
- Blackjack tables and live battleship games are in-memory only—restarts drop active matches. Battleship account W/L, streak and earned ZBS persist with the account; its cleanup timer sweeps every 5 minutes and removes matches idle for 30 minutes (`BattleshipService.cs:23-32,1437-1448`).
