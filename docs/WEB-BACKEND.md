## 1. Startup & topology

Process topology is in ARCHITECTURE.md §1; the web half in one paragraph: `StartWebApi()` runs on a fire-and-forget background task (`Program.cs:77`) inside the same process as the Discord bot. It builds a separate ASP.NET Core DI container and **bridges the Lamar singletons into it by instance** — including `Global`, the ordinary game services, `UserAccounts`, `DiscordWidgetService` and the shared `BlackjackService` — so Discord/passive code and the web mini-game mutate the same live game, table and account state (`Program.StartWebApi`). Web-only singletons are registered on top: `WebGameService`, `GameNotificationService`, `AdminLobbyService`, `GameStoryService`, `BattleshipService`, `ReplayService` and the independent in-memory `ClashService`; `MessageCatalog` is constructed here too, making invalid structured localization fail startup. Every constructor dependency added to a bridged or web-only service must be available in this ASP.NET container; Lamar's automatic `IServiceSingleton` registration does not cross the container boundary.

The deployable remains one host, but Battleship and network Clash rules now have compiler-enforced core boundaries. The executable removes `Battleship/**/*.cs` and `Clash/**/*.cs` from its own compile and references `King-of-the-Garbage-Hill.Games.Battleship` and `King-of-the-Garbage-Hill.Games.Clash`; each class library explicitly compiles only its `Logic/` and `Models/`. The ASP.NET `BattleshipService`/`ClashService` adapters and the single `GameHub` remain in the host, so `GameHub` is the transitional multi-game transport facade rather than shared domain logic (`King-of-the-Garbage-Hill.csproj`; `Battleship/King-of-the-Garbage-Hill.Games.Battleship.csproj`; `Clash/King-of-the-Garbage-Hill.Games.Clash.csproj`).

- JSON is camelCase for both SignalR (`Program.cs:128-133`) and controllers (`Program.cs:136-141`) — the TS interfaces in `signalr.ts` mirror C# DTOs 1:1 modulo casing.
- CORS default policy (`Program.cs:144-160`): origins `http://localhost:5173` (Vite), `http://localhost:3535`, `http://localhost`, `http://kotgh.ozvmusic.com`, `https://kotgh.ozvmusic.com`; any header/method + credentials.
- Middleware order (`Program.cs:162-206`): `UseDefaultFiles` → `UseStaticFiles` (wwwroot = built Vue host, `Program.cs:165-166`) → static `/art` from DataBase/art (`Program.cs:169-177`) → static `/sound` from DataBase/sound (`Program.cs:184-197`) → `UseRouting` → `UseCors` (`Program.cs:199-200`) → `MapControllers` (`Program.cs:202`) → `MapHub` at /gamehub (`Program.cs:203`) → fallback `MapFallbackToFile` to `index.html` (`Program.cs:206`). Every product URL therefore receives the same HTML; the browser registry selects one of five lazy Vue roots, and the three router-owning roots handle their own history-mode routes (WEB-CLIENT.md §2).
- Port: `KOTGH_PORT` env var, default 80, binds 0.0.0.0 (`Program.cs:208-210`). The env var is read **only** here; Config holds `Token`, `AnthropicApiKey`, and the default-off `GameStoryEnglishEnabled` switch (`Config.cs:9-29`, loaded from DataBase/config.json at `Config.cs:16`).
- In `--sim` mode neither Discord nor Kestrel starts (`Program.cs:65-74`); anything that needs a hub context (story push, notifications) simply never runs headless. The same block disables the Haiku service and replay capture (§9).
- Global web-relevant surface: `GamesList`, a bounded `FinishedGamesList`, and three callbacks — `OnGameFinished` and `OnReplaySave` registered by GameNotificationService, plus `SimErrorSink` for the sim harness (`Global`). Game IDs are sequential and unique under a dedicated allocation lock via `GetNewtGamePlayingAndId` (the "Newt" typo is load-bearing API). `StoreFinishedGame` retains at most 128 Ranked final states for 30 minutes; only an authenticated roster owner may read one through the finished-state fallback, while spectator reads and gameplay mutation stay live-game-only (`Global.StoreFinishedGame`/`GetFinishedGame`; `WebGameService.GetGameState`).

## 2. Identity & auth — the trust model (Доверие)

**There is no password, token, cookie, or server-side session for normal play. The client asserts a Discord ID and the server trusts it.** Impersonation is possible by design (hobby-scale); the only OAuth-verified path is the profile widget (§12).

| Channel | Mechanism | Anchor |
|---|---|---|
| SignalR | client invokes `Authenticate(string discordIdStr)`; parsed ulong stored in `Context.Items["discordId"]`, connection registered | `GameHub.cs:61-78` |
| REST | `X-Discord-Id` header parsed per request; missing/unparseable → 401 | `GameController.cs:204-210` |
| Widget | Discord OAuth Bearer token verified against users/@me | `DiscordWidgetService.cs:116-143` |

IDs travel as **strings** over SignalR because Discord snowflakes exceed JS safe-integer range (`GameHub.cs:15-16`; string reply at `GameHub.cs:76`). On disconnect the connection is unregistered and the only "session" — the live connection's `Context.Items` — is gone (`GameHub.cs:45-53`).

**Account ID ranges** (routing in `UserAccounts.GetAccount`, `UserAccounts.cs:78-100`):

| Range | Kind | Created by |
|---|---|---|
| ≤ 1 000 000 | bot | `CreateBotAccount`, PlayerType 404 (`UserAccounts.cs:160-177`) |
| normal snowflakes | Discord human | `CreateUserAccount`, PlayerType 0, prefix `"*"` (`UserAccounts.cs:131-158`) |
| ≥ 9 000 000 000 000 000 000 | web-only | `CreateWebAccount` (`UserAccounts.cs:185-202`) via hub `RegisterWebAccount` (`GameHub.cs:147-173`): validates username 1-32 chars, allocates a monotonic ID (`GenerateWebUserId`, `UserAccounts.cs:204-210`; counter resumed past max existing web ID at startup, `UserAccounts.cs:37-46`), auto-authenticates the connection and replies `WebAccountCreated` |

`PlayerType` remains an authorization/runtime role (0 human, 2 Admin, 404 Bot; legacy value 1 is accepted). Casual/Pro difficulty is now the independent persistent `DiscordAccountClass.GameplayMode`, default Casual. `GamePlayerBridgeClass.AccountGameplayMode` captures the effective mode for one match and is forced to Pro by a Tier-0/PRO assignment. Admin still unlocks raw logs, full fight math, unmasked opponents (§7) and `CreateTestGame`.

**Persistence**: accounts live in a `ConcurrentDictionary` (`UserAccounts.cs:17`) loaded at construction — except in simulation mode, where `UserAccounts.DisableDiskPersistence` starts the store empty and suppresses every write so parallel simulator processes cannot race or corrupt each other on the shared folder (ARCHITECTURE.md §10, finding M52); `IsPlaying` is force-reset for everyone at startup (`ClearPlayingStatus`, `UserAccounts.cs:61-65`). Web create, live join, curated invitation and curated-seat ownership transfer perform their reserved/busy check-and-reserve under that same account monitor; creation captures Ranked starting Elo in the reservation and removes any published partial game plus orphaned roster reservations on failure (`WebGameService.CreateGame`/`JoinWebGame`/`SeatAdminLobbyHuman`; `AdminLobbyService.InvitePlayerAsync`). The guarded 60 s fallback flush and reward-critical writes both route through boolean `SaveAccount`, which locks the account across serialization/write and lets user-triggered transactions restore state when a write fails (`UserAccounts.cs:113-139`). Automatic match settlement instead remains authoritative in memory for that retry if the immediate write fails. `SetLanguage` uses the durable user-action rule: save the normalized account value while holding its monitor, publish the process registry/event only on success, and restore both old values if the write fails (`GameHub.SetLanguage`). Storage reports write success after replacing the canonical JSON through a unique same-directory temporary file; startup loads only `discordAccount-{numericId}.json`, ignoring temporary/backup artifacts (`UsersDataStorage.cs:28-80,83-116`).

Startup also runs the private unknown_bug account migration before normal use: legacy/current chance rows merge, every purchased hidden-weight change is refunded and the remaining internal row is reset to ×1.00; discovery is removed; statistics/mastery are merged under the new private key; history/last-played are renamed; any forced-next-character value is cleared; the two retired achievement IDs are purged from progress/notification queues. The account is immediately saved when any field changes (`UserAccounts.MigrateUnknownBugAccount`). Public stats/store/widget/auth DTOs still filter the migrated private rows.

## 4. SignalR hub `/gamehub` — client-callable methods

`GameHub` (`GameHub.cs:24`). Connection life-cycle: `OnConnectedAsync` logs only (`GameHub.cs:41-45`); `OnDisconnectedAsync` unregisters the connection (`GameHub.cs:47-55`). Rooms: SignalR group `game-{gameId}` joined in `JoinGame` (`GameHub.cs:99-105`), battleship group `bs-{gameId}` and participant-only Clash group `clash-{gameId}`. `JoinClashGame` verifies that `ClashService.GetGameState` can produce a personalized participant DTO before adding the connection; there is no Clash spectator group entrypoint. The hub tracks the current Clash room in `Context.Items`; binding the same connection to a different asserted identity first removes it from the old player map and old Clash group. Connection→player and connection→ordinary-game maps live in GameNotificationService, not the hub (`GameNotificationService.cs:32-35`; `GameHub.BindConnectionToPlayer` / `JoinTrackedClashGroup`).

Call Authenticate first." if unset (`SendNotAuthenticated`, `GameHub.cs:1783-1786`). ## 6. Push model — who sends `GameState` when

1. **Per-action**: the hub pushes to the **acting player's connections only** right after each action (`PushStateToPlayer`, `GameHub.cs:1694-1702`).
2. **Timer**: GameNotificationService polls every 300 ms (`GameNotificationService.cs:97-103`) and broadcasts a game when the round number changed, elapsed time moved > 0.5 s, any player's `IsReady` flipped, or the monotonic `GameClass.StateRevision` changed (`PushUpdates`, `GameNotificationService.cs:225-272`; triggers at `GameNotificationService.cs:250-256`). The revision trigger publishes Gordon's announcement, pause and decision even when the round/timer/readiness snapshot is otherwise unchanged. A `RoundChanged` event accompanies round flips (`GameNotificationService.cs:268-271`). **Finished games are skipped by the timer** (`GameNotificationService.cs:240-248`) — their final state would race the lootbox/achievement stamping in the finish path.
3. **On finish**: the game loop fires `OnGameFinished`, which does the final personalized broadcast, emits `GameFinished`, conditionally kicks off story generation, and drops snapshots/room tracking (kept while a Blackjack table is still open) (`GameNotificationService.cs:78-96`). Active Madara `Вечное Цукуеми` and every unknown_bug roster skip the shared story because either artifact would cross a private-view boundary (`GameNotificationService` finish callback).
4. **Broadcast shape**: `BroadcastGameState` sends a **personalized DTO to every player with a web connection**, then one **spectator DTO** to the remaining connections in the room (`GameNotificationService.cs:178-208`). `SendGameStateToPlayer` is the single-player variant used by game logic (`GameNotificationService.cs:163-171`).
5. Replay saving rides the same finish path: `OnReplaySave` builds + persists the replay and appends its hash to each human's `ReplayHashes` (`GameNotificationService.cs:50-67`). Activated `Вечное Цукуеми` games never invoke that shared callback (`CheckIfReady.cs:850-858`); unknown_bug rosters are rejected again inside both the callback and `ReplayService` as defense in depth.

**Halflife 3 transition pause:** after `CharacterPassives.HandleEndOfRound` but before status reset, regular-score settlement, replay finalization and `RoundNo++`, either a failed human Gordon review or the one-time successful Release/Wait offer parks that game's replay/watch continuation and returns from `CalculateAllFights`. The public top-level pause/deadline fields drive both clients while Gordon alone receives the decision kind/data. `CheckIfReady` retries the pending continuation first on later ticks; before the deadline it skips only that game and proceeds through the rest of `GamesList`. A submitted decision or the 20-second timeout resumes the shared `CompleteRoundAsync` tail exactly once; failure defaults to `freeze`, successful review to `release` (`DoomsdayMachine.ResumePendingRound`; `GordonFreeman.PrepareHalfLifeSettlement`/`ResolveHalfLifeTimeout`).

A converted unit's `BoardingDecks`, `BoardingAbilities` and `BoardingStatuses` are independent mutable snapshots; placement and every movement step atomically register all living deck cells. Shots/collisions/hazards damage the physical boarding deck at the contact coordinate, synchronize the retained source record and kill the unit only after its last deck. Preserved mechanics, statuses and immunities remain active without a one-cell proxy exception: `ballista_immune` and `burn_resist` still guard the hull, while a converted `poison_cone` source contributes and resolves its cone on the physical board that the Boarding hull currently occupies, beginning immediately after deployment. A Down-facing Drakkar registers its complete three-deck hull immediately and resolves its Space aura against hostile physical-board ships only; it never iterates allied summons. Ordinary Boarding hulls devastate 1–2-deck collision targets and die after dealing 4 to a 3–4-deck target. A converted `spawn_cursed_boat` source instead Devastates an eligible target of **any** deck count, remains alive and enters `WaitingForDirectionChoice`; the caller-only course DTO validates the entire rotated hull. `AdvanceTurn` immediately consumes Penalty/Stun in priority order, clears `ConsecutiveWarmingMisses`, emits one queued public skip event per cancelled turn and keeps switching until the current player can act; `PushBattleshipStateToAll` drains those events before publishing the already-advanced state. Scout and Boarding reconnaissance remains deferred exact-cell data; a living Mast gates exact opposing summon/ability messages. Any ordinary shot into an already destroyed deck is a miss; Evil Incendiary is the documented exception. Light Wood stores one latest pink Ballista-dodge origin on clean revealed miss water—not an exact-deck snapshot—and clears it on the next dodge or removal. Every trail/death entry remains ordered `SummonMarkerDto { SummonId, Type, IsBoardingShip, SourceShipName }`; the generic legend is a client grouping, not lost source identity (`BattleshipService.AdvanceTurn` / `TakePendingTurnSkipEvents` / `MapBoard` / `MapFogBoard` / `MapSummonMarker`; `BattleshipGameEngine.CreateSummonFromPending` / `GetLiveBoardingOccupiedCells` / `TryPlaceSummonOnBoard` / `MoveSummons` / `ResolveSummonEntry` / `RefreshPoisonZones` / `ProcessPoisonCones` / `ProcessSummonHit` / `HandleSummonCollision`).
- Matryoshka replacement hardening is part of that resolution boundary. CAPTURE-disabled, `Devastated` and structurally removed-by-ramming stages are suppressed because none is an ordinary passive death. The unselected cell stores a typed red historical wreck; each public click coordinate is the unique opposite endpoint of its subset, while placement uses the subset's true first-cell anchor. Multiple wrecks are globally sequential, and the enemy receives only the designer-supplied exact opening line. ## 11. LLM services (outbound Anthropic API)

## 13. Per-account localization

`Authenticate` now resolves the account's persisted language under its monitor, registers it for Discord projection and returns it in `Authenticated`. This makes the account authoritative after login instead of allowing the browser's initial default to overwrite it. `GameHub.SetLanguage` normalizes `ru` or `en`, saves while holding the same account monitor used by other durable user actions, updates the process locale registry only after success, emits `LanguageChanged` to every active connection for that account, returns the saved language and immediately re-pushes current personalized state. A failed write restores the old account/registry values and emits `Error` (`GameHub.Authenticate` / `SetLanguage`).

New authored copy lives in product-scoped root `Localization/*.messages.json`. A definition has a stable key prefixed by its catalog's `product`, both `ru` and `en`, explicit `public|owner|server` visibility and the same named placeholders in both languages. The project copies those files to deployed `Localization/`; constructing the singleton `MessageCatalog` validates every file, duplicate, prefix, language, visibility and placeholder set at startup. Discord/headless `GameLocalization.MessageForUser` reaches the same catalog through an explicit lazy factory rather than `Lazy<T>`'s reflection-only parameterless-constructor path. `LocalizedMessage` carries a stable key plus arguments and `LocalizedText` carries paired generated prose; `MessageCatalog.Render` chooses a viewer locale without changing gameplay identifiers (`King-of-the-Garbage-Hill/Localization/MessageCatalog.cs`; `King-of-the-Garbage-Hill/Localization/LocalizedText.cs`; `GameLocalization.StructuredMessages`; `King-of-the-Garbage-Hill.csproj`; M217).

The former general catalog is retained as a **legacy compatibility layer**. `DataBase/localization.en.json` is copied to deployed `DataBase` and loaded by `GameLocalization`; longest-first fragments cover markup-split and partially projected historic/replay forms. Dynamic rules remain idempotent across canonical and partially translated snapshots (`GameLocalization.cs:34-55`). Character flavor selected by `PhraseClass` continues to use `phrases.en.json`, whose startup validation enforces group/count and exact Russian source parity (`PhraseLocalization.cs:19-69,165-198`). Existing Gordon/Jon direct `PhrasePayload` records and dynamic Witcher `PhraseV2` payloads also remain replay-safe. ## 14. Account-reward transaction boundary

All account-economy operations synchronize on the `DiscordAccountClass` instance: the finish path settles account/history/mastery/ZBS/quest/top-two-box/achievement/statistics together; Battleship, Daily Quest, loot, paid draft picks and both Discord/web stores use that same account monitor (`CheckIfReady` game-end settlement; `BattleshipService` reward methods; `QuestService` settlement; web store methods; `StoreReactions.ReactionAddedStore`). This prevents simultaneous reward, reroll, pick or shop actions from losing a balance/box/progress update.

The conditional +69 ZBS TheBoys government salary is included inside that same finish transaction before saving (`CheckIfReady.HandleLastRound`; `TheBoys.ShouldAwardGovernmentSalary`).

For a Pro match seat, placement ZBS and the TheBoys government salary are doubled, and an alive reward-top-2 finish grants two loot boxes instead of one. Ranked games are unjoinable one-human/five-level-3-bot games available only to accounts whose selected future mode is Pro; ordinary web games explicitly use the level-4 Legacy+ default. At placement, rating below 1200 uses ELO `+10/+5/+1/0/−1/−5` for factual places 1–6; 1200–1400 inclusive uses `+20/0/0/−1/−3/−5`; strictly above 1400 uses `+20/0/−1/−3/−5/−10`. `FinishGame` cannot substitute the creator, and an unsettled old «21» entitlement blocks a second Ranked create, so the owner row and receipt remain match-specific (`RankedElo.GetPlacementDelta`; `CheckIfReady.HandleLastRound`; `GameHub.CreateRankedGame`; `WebGameService.CreateGame`/`FinishGame`).

Daily Quest day/week initialization is a durable user-visible mutation: `RequestQuests` snapshots the complete quest/economy state, normalizes/migrates with one UTC timestamp, saves before sending, and restores on failure. `RerollDailyQuest` uses the same contract, including replacement progress and any immediately earned card/daily/mastery/weekly rewards (`QuestClass.cs:283-355,414-508`; `GameHub.cs:675-742`). Game-end progress uses the ordinary settlement policy: retain the completed in-memory transaction for periodic retry if the immediate save fails. Full semantics: [DAILY-QUESTS.md](DAILY-QUESTS.md).

Loot results are retry-safe rather than client-animated randomness. `QuestData.LastLootBox` persists the last `OpeningId`; until acknowledged, every V2 open returns it without another debit/credit. `RequestQuests` returns that unacknowledged record with current account totals and the guaranteed-character queue head/count for reload/reconnect recovery (`GameHub.cs:675-710`). `OpenLootBoxV2` snapshots and restores ZBS, inventory, pity/result state and `LootBoxCharacterQueue` around the save; no loot transaction reads or mutates `CharacterChance`. Acknowledgement retains the same durable boundary. Legacy `OpenLootBox` acknowledges inside the transaction so cached clients without the new acknowledgement call do not become stuck (`QuestService.OpenLootBox`; `OpenLootBoxCore`/`CaptureLootBoxAccountState`). The reveal animation never determines any reward.

New results use `SecureRandom`: reward amounts use its inclusive bounds and rarity rolls use 10,000 equally likely outcomes with cumulative cutoffs 50/300/1500/4000, exactly preserving the published 0.5/2.5/12/25/60% base distribution (`QuestService.RollLootBoxTier`; RNG implementation `SecureRandom.cs:17-25`). The selected public character is another secure draw; Epic limits it to Tier 1–2 and Legendary to Tier 1. Pity upgrades only a tenth consecutive below-Rare natural result; the upgraded result receives the complete Rare ZBS reward and does not replace a natural Rare+.

User-triggered economy writes are durable before confirmation: Daily Quest, loot, achievement acknowledgement, paid draft, and both store transaction paths save while holding the account monitor, then restore their exact in-memory snapshot before returning a retryable error if replacement fails (`WebGameService` store methods; `StoreReactions.ReactionAddedStore`). `SaveAccount` reports the atomic-replace result (`UserAccounts.cs:113-139`; `UsersDataStorage.cs:28-80`). A real-player game-end save failure is critical-logged and retains its settled in-memory state for the periodic retry; bot accounts deliberately skip the immediate disk write (`CheckIfReady` game-end settlement).

Achievement V2 generally filters unknown legacy IDs rather than inferring retroactive rewards from match history (`AchievementClass.cs` catalog/board filtering; `GameHub.cs` achievement board). The two retired private-character IDs are the explicit cleanup exception: startup removes their stale progress and acknowledgement entries without clawing back already-issued rewards (`UserAccounts.MigrateUnknownBugAccount`). Daily Quest V1 instead has an explicit same-day economy migration: paid legacy days become settled without a second payout; unpaid days begin V2, while loot state is preserved (`QuestClass.cs:283-355,734-797`).

## 15. Known quirks & pitfalls (backend)

- **Asserted-ID auth**: any client can claim any Discord ID (§2). Never build features assuming web identity is verified; the only verified flag is `WidgetAuthorized` (`DiscordWidgetService.cs:141`).
- **REST is a subset** — new player-facing actions must be added to the hub (and usually only the hub); adding them to GameController is optional parity. Gordon's announce/wake/release-decision trio is an intentional parity exception (§3).
- **ARAM has hub/REST methods but no web UI** — AramReroll/AramConfirm are callable and the reroll counters are serialized, but the Vue client never renders an ARAM pick screen (finding **m24** in AUDIT-FINDINGS.md; WEB-CLIENT.md §13).
- `Attack` pushes state even when rejected (`GameHub.cs:228-235`) — the client relies on this to re-sync after refusals; other actions push on success only.
- Finished games are invisible to the 300 ms timer (§6) — if you add finish-time data to the DTO, populate it **before** the finish callback fires or it will never reach clients.
- New per-player web state needs the whole §7 pipeline: DTO member (`GameStateDto.cs`), mapper case with the right isMe/isAdmin gate (`GameStateMapper.cs`), TS mirror + widget (ARCHITECTURE.md §7 steps 11-14). Missing the gate = information leak to opponents/spectators.
- `KOTGH_PORT` is env-only (`Program.cs:208`); Config carries the bot token, Anthropic key, and default-off `GameStoryEnglishEnabled` switch (`Config.cs:9-29`).
- Discord IDs cross the hub as strings; the server parses with `ulong.TryParse` (`GameHub.cs:69-74`) — never let the client send them as JS numbers.
- Blackjack tables, live battleship games and network Clash matches are in-memory only—restarts drop active matches. Battleship account W/L, streak and earned ZBS persist with the account; its cleanup timer sweeps every 5 minutes and removes matches idle for 30 minutes (`BattleshipService.cs:23-33,1647-1660`). Clash has no persistent account meta or replay; its five-minute sweep removes only idle lobby/finished records after 30 minutes, not abandoned active phases (`ClashService.CleanupStaleGames`).
