## 1. Stack & build

- Vue 3.5 + TypeScript + Pinia 2 + vue-router 4, SignalR client `@microsoft/signalr` 8, icons `lucide-vue-next` (package.json dependencies). Scripts: dev = vite, build = vite build, serve = vite preview, `test:99lc` / `test:empires` = focused Vitest suites, `test:99lc:e2e` / `test:empires:e2e` = Cypress browser scenarios, type-check = vue-tsc (broken in this environment — **`pnpm build` is the verifier**, per AGENTS.md), lint = eslint --fix.
- Build outputs **straight into the backend's wwwroot**: `outDir` ../../King-of-the-Garbage-Hill/wwwroot with `emptyOutDir` (`vite.config.ts:15-19`) — deploying the backend ships the SPA.
- Dev proxy forwards `/api`, `/gamehub` (ws), `/art`, `/sound` to the **production EC2 box** http://3.65.44.127 (`vite.config.ts:24-44`) — local dev talks to prod by default; a commented localhost:3535 alternative sits in the .env file. Prod build uses same-origin: .env.production sets empty VITE_API_HOST and VITE_SIGNALR_HUB=/gamehub.
- Path alias `src` → ./src (`vite.config.ts:10-14`); Vitest uses jsdom plus `src/setupTests.ts`. The focused 99LC suites cover configuration/loading validation (including spawn geometry, route capacity and every equipment mode), deterministic capped generation, death/retry erosion, persistent basic combos, all five gesture sequences, standard/raw-Sony gamepad normalization and controller route entry. Its Cypress flow exercises route selection and the hold-follow-up attack through the browser Gamepad API boundary, plus Builder persistence versus fresh-generation application (`features/last-chances/*.spec.ts`; `cypress/e2e/last-chances.cy.ts`).
- Browser localization is assembled by the Vite `publicLocalizationPlugin`: it emits the virtual `virtual:public-localization` module from definitions whose `BrowserCatalog` is not false, then case-insensitively sanitizes exact/term/phrase catalogs against every explicitly private name, description, localization variant and passive before Rollup sees them. Content from a `BrowserCatalog: false` definition therefore does not ship in the static browser bundle; an authorized owner can still receive their own dynamic DTO text at runtime (`vite.config.ts` `publicLocalizationPlugin`; declaration `src/virtual-public-localization.d.ts`).
- Gotcha: `VITE_API_BASE` is read in two places but **never defined** in any env file — it resolves to '' so fetches stay relative (`replay.ts:11`, `Lobby.vue:9`); works only because of the proxy/same-origin setup.

## 2. App shell & routing

- **Game version corner label** (`App.vue:260-261`, computed `App.vue:25-32`): faint fixed bottom-right `v4.1.8`-style label on game/spectate/replay routes only, stripped from `gameState.gameVersion` (`Версия: X` → `vX`); replays show the version recorded in the replay file, `pointer-events: none`, hidden while `gameState` is null.

## 3. Identity & session (client side)

Two login paths in `LoginProcess.vue`: a numeric **Discord User ID** input validated `/^\d+$/` with a "Copy User ID via Developer Mode" hint, or a **web username** (max 32 chars). Its buttons use the parent/store busy state and an inline ARIA alert, so a failed initial transport start re-enables a visible retry instead of leaving the login poisoned (`LoginProcess.vue:1-87`; `App.vue` `connectAndAuth`/`connectAndAuthWeb`/`handleWebLogin`). `App.vue` connects + authenticates and persists `discordId`, or lets the server mint a web account; the store saves `kotgh_web_id`/`kotgh_web_username` when `WebAccountCreated` arrives (`game.ts:317-339`). `restoreWebSession` re-authenticates from those keys (`game.ts:822-833`). There is no password — see the trust model in WEB-BACKEND.md §2.

## 4. SignalR client (`signalr.ts`)

Singleton `signalrService` (`signalr.ts:1644`); hub URL from VITE_SIGNALR_HUB, default /gamehub (`signalr.ts:3`).

- **Lifecycle**: `connect()` builds the connection `withAutomaticReconnect` at 0/1s/2s/5s/10s/30s and registers every handler (`signalr.ts:1067-1182`). A failed first start or exhausted disconnected instance is stopped and discarded so explicit login can build a fresh transport; reward invokes additionally require an authenticated session, not merely a connected socket (`signalr.ts:1053-1083,1194-1260`). **On reconnect it re-authenticates with the remembered ID and re-joins the remembered game** (`signalr.ts:1184-1195`).
- **Server events → store** (handlers assigned in `useGameStore.connect()`, `game.ts:159-382`): quest and achievement state retain their existing recovery behavior; `StoreState` replaces the full owner-only shop snapshot after reads and durable transactions, clears the matching busy/error state, and mirrors its ZBS balance into an already-loaded quest board (`game.ts:284-293`). Re-authentication refreshes the shop only after that surface has been opened once (`game.ts:341-349`).
- **Invoke wrappers** mirror the hub 1:1 (WEB-BACKEND.md §4), including Gordon's `announceHalfLife3(gameId)`, `wakeGordon(gameId)` and serial-protected `resolveHalfLife3Decision(gameId, decisionSerial, 'freeze'|'postpone')` (`signalr.ts:1472-1485`), the character-store request/adjust/reset methods, and account-level `requestDoomFortress`/`equipDoomModule`.

## 6. Stores (Pinia)

**`useGameStore`** (`game.ts:54`) — the core store.
- State refs (`game.ts:57-97`): identity/game/meta state plus quest state/loading/error/reroll ID, resumable `lootBoxResult`, store-owned loot-modal priority, achievement board/full celebration queue/loading/acknowledgement-error state, character-store snapshot/loading/action/error state, character list and `doomFortressState`.
- Getters: `myPlayer` by myPlayerId — null for spectators (`game.ts:96-103`); `opponents` (`game.ts:105-110`); `isMyTurn` = not paused, not ready and not skip, with round-8 Madara always locked false (`game.ts:118-123`); `roundTimeLeft` = turnLength − timePassed; `isInGame`, game/admin flags and character helpers. `isTerminalMode` and `myTerminalState` are generic owner-only selectors over the matching `Player` projection; components never detect this presentation by a character/passive string (`game.ts` `isTerminalMode`/`myTerminalState`).
- `connect()` (`game.ts:154-364`) wires every SignalR callback; the `GameState` handler additionally diffs own stats for sounds, **auto-joins Blackjack when newly dead to Kira**, and captures full finish-time achievement entries once per game (`game.ts:175-238`). Quest/board callbacks restore server-held Daily Quest/loot/achievement state (`game.ts:242-275`); authentication hydrates both reward families (§4).
- Action wrappers mirror the hub and layer client SFX: block plays block + Geralt meditation + turn-10 layer, levelUp records `pendingLevelUp` for sound resolution, and moral exchanges play once per round. Gordon's wrappers reject announce/wake locally during a paused transition and submit the server-supplied decision serial with the release choice (`game.ts:525-545`); the backend remains authoritative.
- Daily Quest requests expose dedicated loading/error state; one in-flight request queues at most one trailing refresh (so a call spanning UTC midnight cannot strand yesterday's board), and `rerollDailyQuest` keeps the chosen card busy until the server sends its durable replacement (`game.ts:685-717`; hub wrappers `signalr.ts:1512-1518`). Loot wrappers keep acknowledgement explicit: `openLootBox` invokes `OpenLootBoxV2`, waits at most 12 s for the server event and exposes the idempotent retry path; acknowledgement refreshes current inventory, and `clearLootBoxResult` removes only the matching result (`game.ts:719-767`; wrapper `signalr.ts:1520-1526`). Achievement dismissal snapshots the IDs shown but **keeps the popup/queue visible** while saving; only a successful selective acknowledgement removes them, while failure stays inline and retryable (`game.ts:795-827`). Logout hard-resets quest/reward/modal/ack state (`game.ts:396-444`).
- Character-store wrappers keep one account transaction in flight, expose page-local loading/errors, and rely on each returned full snapshot as the durable confirmation; requests, ±1/±10 changes, one-character refunds and refund-all live at `game.ts:815-873`.

**`useReplayStore`** (`replay.ts:122`) — replay playback. State: replayData/raw currentRound/currentPlayerIndex/currentFightIndex (`replay.ts:122-129`). The round-window adapter detects format v2 versus legacy boundary files (`replay.ts:21-54`): v2 uses actual round numbers and explicit `preFightPlayers`; legacy raw URL key K remains K for old deep links but is displayed as logical combat round K−1 and obtains pre-fight state from the preceding boundary (`replay.ts:133-166`). `computedGameState` (`replay.ts:177-269`) **reconstructs a full GameState** from the chosen round + player perspective so normal in-game components render replays unchanged: `buildShiftedPlayer` takes fight-facing actions/character/passive state from pre-fight and settled score/place/death/breakdown from the atomic result, discarding its next-round status/log buffer (`replay.ts:56-120`). V2 appends only explicit HandleLastRound personal/global suffixes (`signalr.ts:1001-1019`); legacy final files retain their inseparable raw final personal buffer (`replay.ts:48-54,165-166,208-258`). Other players' private blocks remain stripped (`replay.ts:199-240`), and replay state is finished/admin-visible (`replay.ts:243-268`). Because captured private snapshots reflect the original player's presentation locale (`ReplayService.cs:301-339`), the Vue boundary re-localizes canonical and older mixed phrase records for the current replay viewer (`Web/VueClient/src/i18n.ts:146-196`). `loadReplay` fetches the anonymous REST payload and starts on the final playable logical round (`replay.ts:273-295`). Alignment fixtures cover legacy URLs/logs, v2 numbers, skip isolation, post-setup score/death/breakdown and final personal/global settlement (`replay.spec.ts:66-223`).

**`useBattleshipStore`** (store/battleship.ts) — minigame state/lobby/placement/combat/VFX state with its own signalr callback wiring; independent of the main game store (§12).

## 7. Pages & flows

- **Fight Calculator** (`FightCalculator.vue`, route `/fight-calculator`): local-only combat lab for two teams of up to six units. Each unit can configure HP, movement speed, primary/secondary/dagger weapons, mastery, helmet/mail/padding/plate armor and talents. The seeded engine (`features/fight-calculator/engine.ts`) resolves mirrored slots, free-opponent fallback and survivor collisions while logging range, fatigue, techniques, penetration, armor/weapon degradation and status effects step by step. The baseline catalog (`features/fight-calculator/catalog.ts`) transcribes the supplied weapons-and-armor spreadsheet; the Balance dialog can edit mechanics/catalog values and add custom weapons, armor or talents. Named profiles, their balance copies and team layouts stay browser-local under `kotgh_fight_calculator_profiles_v1`; this surface has no SignalR or backend contract.
- **99 Last Chances** (`LastChances.vue`, public route `/99lc`): client-only real-time vertical slice with a seeded six-normal-tier-plus-boss run graph, room choice, isometric combat arena, fixed room contents across death retries, configurable Chance loss/stat erosion and a built-in definition editor. It is independent of the main game store and can be opened without authentication; there are no account rewards or hidden server state in this prototype.
- **Lobby** (`Lobby.vue`): polls only `refreshLobby` every 3 s, while Daily Quests refresh on authentication/mount, visibility return and the board's UTC countdown rollover. Its persistent Rewards hub shows live ZBS, pending box inventory, Rare+ distance/base Legendary chance, the next guaranteed loot character plus remaining FIFO count, achievement completion/new badge and current-catalog totals (`Lobby.vue` reward hub). `DailyQuestBoard` renders the typed bilingual 2/3 daily + 3/3 mastery path, streak, explicitly explained 5/7 weekly journey, free reroll and all load/error/empty states; a replaced card is announced and receives focus after the old reroll button disappears (`DailyQuestBoard.vue:1-604`). The admin-only “Test New Game” button lazily requests the viewer-scoped `CharacterList`; persistent `PlayerType == 2` accounts receive the ordinary Tier ≥ 0 choices plus unknown_bug from the server, while its definition remains absent from the static bundle and regular callers receive only the unchanged public list used by achievement filters (`Lobby.vue` `openTestGamePicker`; WEB-BACKEND.md §4). The loot flow still owns modal priority and keeps its bounded retry/acknowledgement handoff unchanged (`Lobby.vue` loot flow).
- **Achievements** (`Achievements.vue` + `AchievementBoard.vue`): dedicated `/achievements` center (`router.ts:65-69`). It requests the board/character list, shows completion and reward summaries plus three nearest non-secret completions, then supports category/status/rarity filters and genuinely bilingual search across both EN/RU name, description and secret-hint pairs plus character names. Cards render character avatars, best-single-match progress, secret hints, rewards, rarity, unlock date, loading skeletons and retry/error states (`AchievementBoard.vue:22-197`; `AchievementBoard.vue:200-434`).
- **Game** (`Game.vue`, the main view): existing three-column play surface and ordinary finish flow are unchanged. For a fooled Вечное Цукуеми viewer only, the synthetic final FightLog plays before the podium/winner theme (15-second safety fallback); Madara and a Gordon who reserved Wake receive the authoritative ending without synthetic fights, while unknown_bug receives the authoritative ending with any real fight its immune action produced. `prefers-reduced-motion` bypasses both illusion waiting and the fixed five-second podium/confetti gate, and achievement popups wait for the same illusion handoff (`Game.vue` `finishPresentationPending`/`revealFinishedGame`; server projection in WEB-BACKEND.md §7). On every authenticated **non-game route**, `App.vue` hosts the same queue unless the loot flow currently owns modal priority.
- **Gordon action/transition flow**: while Halflife 3 can be announced, Gordon's ordinary Block slot becomes the one-shot `Halflife 3` action; `Проснуться` appears beside Skip only when the owner DTO says G-Man can wake him. A public transition pause forces `isMyTurn=false`, disables every inline action and attack affordance, hides `RoundTimer`, and mounts `HalfLife3Transition` in the authenticated game page. Gordon receives a non-dismissible, focus-trapped release-review dialog with the server's failure text, raw points, multiplier, exponent, final total, postponement count, exact attempt-specific button labels and deadline; every other player on that page receives the full-screen wait overlay. An expired client countdown disables both choices while the server applies the authoritative timeout freeze (`Game.vue` `gordonState`/`transitionPaused`; `HalfLife3Transition.vue`; `game.ts:118-123,525-545`).

## 12A. 99 Last Chances prototype

The `/99lc` surface is a self-contained browser prototype built on Vue plus a native Canvas 2D engine under `features/last-chances/`; it does not call REST, SignalR or the account economy. The engine renders one configured room at a time through an isometric projection and performs collision and combat on world coordinates while the run plan remains seeded and immutable. Keyboard/mouse, touch and normalized gamepad controls feed the same movement and two-hand gesture recognizers. A controller-only player can select and enter available route nodes before combat; the selected node and connected-pad state remain visible.

Each new generation creates an immutable seeded graph with six configurable normal tiers and a boss node. Every next-tier node receives an incoming edge and no parent exceeds `graph.choicesPerNode`; definitions whose available edge capacity cannot satisfy both rules are rejected. Each schema-v2 room provides at least two named spawn layouts. A node selects one layout from its seed, records its `spawnLayoutId`, and uses only that formation's exact authored points, so room archetype, formation and graph links remain stable when the player dies. Validation requires every eligible layout to hold that room's maximum enemy count, fits the player and largest eligible enemy circle inside room bounds and outside obstacles, rejects overlapping enemy circles, and keeps every enemy at least the combined radii away from `playerSpawn`. A retry returns to the opening choice with enemies restored while subtracting the current tier's configured Chance cost and applying the configured health, mind, attack, speed and armor erosion; a deliberately requested new generation replaces the seed and restores the initial 99 Chances. Room completion exposes only connected next nodes in the route-map overlay (`plan.ts` `makeNode`/`connectTiers`; `config.ts` `validateGraphCapacity`/`validateSpawnGeometry`).

Each active input owns five data-defined attacks keyed by `tap`, `doubleTap`, `doubleTapHold`, `hold` and the legacy internal key `holdThenDoubleTap`. The latter means one hold/release followed by one short repeat press inside the configured follow-up window — two presses total — and is labelled “Hold + tap”. Ordinary taps never enter the cooldown map: each hand advances through its authored, per-weapon basic-attack sequence while the next tap arrives within `input.tapComboWindowMs` (900 ms by default). Specials and a temporary pause do not erase a live combo; a new room/attempt does. Per-hand HUD feedback exposes the current press, double-tap window, second press and hold-follow-up window with countdown/progress, so an input still being classified is distinguishable from an ignored input (`features/last-chances/gestures.ts` `LastChancesGestureRecognizer`; `engine.ts` `performAttack`/`advanceTapCombo`; `components/last-chances/WeaponCooldowns.vue`). Attack definitions choose one of the supported melee-arc, burst, projectile or dash executors and carry all damage, special cooldown, active-time, range, radius, arc, knockback, pierce, projectile and visual values. Melee and burst collision remains active for the authored duration, includes the authored radius, honors directional arcs, and can hit an entering target once; a burst's live reach expands with its rendered wave. Projectiles and dashes retain their moving collision executors, and every executor enforces the same `pierce + 1` unique-target budget. Enemy definitions similarly own hitbox, health, speed, idle scan rate, preferred chase distance, damage, sight, notice delay, alert pause, attack timing and mental-damage values; their visible `!`/`!!` transition mirrors the authored notice-then-hesitate requirement (`engine.ts` `performProjectile`/`performDash`/`startActiveArea`/`updateActiveAreas`/`updateEnemies`).

Schema v2 turns the weapon array into a catalog rather than a hard-coded pair. `loadout.primaryWeaponId` and nullable `secondaryWeaponId` resolve `twoHanded`, `eitherHand`, `primaryOnly`, `secondaryOnly` and `hybrid` modes: a two-handed weapon supplies separate five-gesture sets to both inputs, an either-hand definition may occupy either or both slots, and an unpaired hybrid uses its own secondary set until another valid secondary is equipped. Empty secondary slots are valid. The shipped spear is hybrid: spear plus knife uses the knife on the secondary input, while removing the knife exposes the spear's separately authored second-hand moves. Valid schema-v1 definitions without `loadout` retain their fixed left/right behavior and fallback timing/AI fields; the concrete previously shipped v1 browser/file definition is deep-cloned, has its obsolete tap cooldowns repaired, and moves each known unsafe spawn only when the override's current bounds/obstacles/player geometry says the old circle is unsafe and the replacement is safe. Schema v2 is never rewritten. Loader, save, engine and Builder JSON paths share `migrateLastChancesConfig`. The engine and HUD both consume `resolveLastChancesLoadout`, so Builder JSON, validation, controls and combat cannot disagree (`features/last-chances/equipment.ts`; `types.ts` `LastChancesWeaponDefinition`/`LastChancesLoadoutDefinition`; `config.ts` `migrateLastChancesConfig`/`validateWeapons`; `pages/LastChances.vue`; `components/last-chances/BuilderDrawer.vue`).

Gamepad polling is normalized by `features/last-chances/gamepad.ts`: the currently active connected pad is selected across multiple devices, standard reports use canonical axes/buttons, and known unmapped Sony/DualSense reports receive their raw face-button and right-stick remap. The default GDD bindings are Square/button 2 for the left hand and Cross/button 0 for the right; route-map navigation and combat share the same adapter, while the control dock exposes connection, device and mapping-profile status (`gamepad.ts` `createLastChancesGamepadAdapter`; `engine.ts` `pollGamepad`; `public/99lc/game-config.json`).

The default definition is fetched with `no-store` from `/99lc/game-config.json`, so deployed configuration can be replaced without recompiling the SPA. The in-game Builder validates a complete definition before applying it, offers quick controls for common player/Chance/input/attack/enemy values (including the basic-combo window and both externalized enemy movement controls), exposes the full JSON for structural changes, and supports browser override, clear, file import and JSON export. “Save browser override” changes only the persisted local definition and leaves the active attempt untouched; “Clear override” likewise changes only future-load persistence; “Apply & start fresh generation” explicitly discards the active attempt and creates generation 1 from the draft. Browser overrides are local prototype state and do not mutate the server file. Adding content within the existing room, enemy, spawn, weapon and attack schemas is configuration-only, while a genuinely new attack executor or interaction semantic still requires code (`components/last-chances/BuilderDrawer.vue`; `pages/LastChances.vue` `saveBuilderOverride`/`clearBuilderOverride`/`applyBuilder`).

The current milestone implements the mechanics/control vertical slice as schematic Canvas 2D. That is an explicit prototype implementation boundary, not the final visual target in the brief: its requested 2D locations with 3D characters/interactives are still unimplemented. The supplied Discord images and audio were reviewed as visual, enemy, progression and mood references; several are reference material rather than production-cleared runtime assets, so none are silently shipped and the current renderer remains original procedural geometry/effects. Broader GDD/Discord product vision remains deliberately outside this milestone: distinct chest/rest/event interactions, loot/traps/builds/economy, merchants, authored story/horror encounters, animation/3D production art, backend checkpoints, account/meta progression, multiplayer/spectator state and cross-device saves are not implemented.

## 12B. Empire's Endgame

The `/empires-endgame` surface is a self-contained, deterministic browser game. A campaign alternates full-deck Durak against God, scoring/divine-gift resolution and an empire-planning phase (`pages/EmpiresEndgame.vue`; `features/empires-endgame/engine.ts` `EmpiresEndgameEngine`). The 53-card deck contains ranks 2 through Ace in all four suits plus the Joker/Jester. It implements legal same-rank throw-ins, same-suit/trump defence, the unbeatable configurable Joker, a pending-take window in which the attacker can finish throwing cards, attacker-first refill and role retention/swap. Engine-backed take/finish controls are invalidated on every state emission, and the runner automatically closes a resolvable attack when the player's hand is empty, so a bout cannot wait for a hidden control. The left deck is deliberately non-interactive and labelled as automatic refill; its visible bottom card is `deck[0]`, while normal draws use `pop()` from the other end (`pages/EmpiresEndgame.vue` `runGodTurns`/`trumpCardView`; `components/empires-endgame/DurakTable.vue`).

Every card definition owns editable upright and reversed forms, including its independent card name, suit/rank, time cost, value, image, passive title and effects. Cards retained between cons contribute their current-side effects; the empire receives 59 days minus the retained cards' time costs. Hand-card flag contributions are serialized separately from permanent gift/event/research flags and removed when that empire phase ends, so old hands cannot leave ghost bonuses; legacy schema-v1 empire/event saves that predate this ownership field reconstruct it from the held card faces before play resumes. The authored `peasantProductivityPercent` scales only operational farm output, `recruitmentDisabled` prevents every recruitment order without spending anything, and `starvationLossMultiplierPercent` scales the ordinary half-deficit population loss (`engine.ts` `heldCardFlagBonuses`/`recordCardFlagBonuses`/`clearCardFlagBonuses`, `recruitUnits`, `cityProduction`, `finishEmpireInternal`). The authoritative notes currently specify complete effects for 11 cards, so the remaining catalog entries are deliberately visible editable placeholders rather than invented rules (`public/empires-endgame/game-config.json`; `components/empires-endgame/EmpireCard.vue`; `components/empires-endgame/DurakTable.vue`).

Ten bouts form a con. Configurable performance rules award card improvement/restoration points, then three weighted divine gifts are drafted. Gift weights may react to performance and gift effects may be one-shot or repeat at each empire phase. The card Council renders retained cards with their native light/inverted surfaces, lets a card be selected, explains insufficient points, and keeps improve/restore actions scoped outside the card surface (`pages/EmpiresEndgame.vue` `councilCards`/`selectCouncilCard`). The default empire spans five regions, ten subregions and thirteen cities; selecting a region presents its normalized one-fifth map viewport, polygon subregions and editable terrain/river/city objects. Each city has farm, lumber, mine, smithy, barracks, unique and municipal placement semantics. A building must occupy a compatible slot before it can be upgraded; purchased levels persist while insufficient workers automatically shut down the highest operational levels first. Building prerequisites, technology prerequisites, facility locks, worker demand, construction days, food and resources are all enforced (`engine.ts` `placeBuilding`, `upgradeBuilding`, `recomputeOperationalBuildings`; `components/empires-endgame/EmpireMap.vue`; `components/empires-endgame/CityView.vue`).

Food consumption is calculated from the city's population-class definitions plus recruited-army upkeep. Recruitment consumes configurable resources and deducts each unit's population cost from the city's actual population, ready military pool and recruitable class distribution; it charges time once per order, requires its same-city operational building dependencies and rejects orders whose post-recruit workforce, production and food consumption would be unsafe. At empire end, a food deficit removes half the shortfall from population. The configured exclusive production boost may target only one eligible farm/lumber/mine at a time and defaults to 200%; assigning it to another target moves the boost (`engine.ts` `cityFoodConsumption`, `cityArmyFoodUpkeep`, `recruitUnits`, `consumeRecruitmentPopulation`, `assignProductionBoost`).

Runtime definitions and campaign saves are separate, versioned local data. Seeded game state makes the same definition, seed and player choices reproducible; browser autosave supports continuing the local campaign, while JSON import/export provides explicit backup and transfer. Old schema-v1 saves receive defaults for new placement, unit and production-boost state plus reconstruction of active held-card flag ownership during restoration. The surface has no REST, SignalR, account-economy, multiplayer or cross-device synchronization contract (`features/empires-endgame/config.ts`; `features/empires-endgame/persistence.ts`; `engine.ts` `validateAndCloneSnapshot`).

The integrated constructor treats game content as data rather than hard-coded UI and remains available from every campaign phase. Its JSON-safe clone boundary accepts Vue-reactive definitions without sending a Proxy through `structuredClone`. It includes direct card/form, building-level, technology/reform, divine-gift and event fields; a draggable building dependency graph; draggable technology nodes and links; region/subregion/object inspectors on the live map; population editing; common rule controls; and full validated JSON import/export for the complete schema, including units and advanced effects. Technology coordinates are authored world pixels on a scrollable/pannable canvas sized from all node extents; the same coordinate system is emitted by constructor drag, while position-less custom nodes receive a non-overlapping grid beyond the authored extent. The detail pane states full costs and the first unmet resource/flag/building/technology dependency. Saving constructor changes intentionally starts a new campaign with the validated definition instead of rewriting a running state (`features/empires-endgame/config.ts` `cloneEmpiresConfig`; `components/empires-endgame/BuilderDrawer.vue`; `BuildingDependencyEditor.vue`; `TechTree.vue`; `PopulationDialog.vue`; `pages/EmpiresEndgame.vue` `technologyNodes`/`saveEditor`).

Deterministic QA mode is entered only with `?qa=1`; `scenario` selects one of `pending-take`, `empty-hand-pending-finish`, `divine-gift`, `empire-council-with-points`, `event`, `victory` or `defeat`, and `seed` makes it reproducible. QA snapshots bypass the normal local save and expose a small scenario/reseed/reload/autoplay panel. New Campaign, save import and constructor save/reset are also ephemeral in QA and never write or clear the production campaign/configuration stores. The harness validates complete card location and phase invariants, lists every legal player action, detects no-action stalls with a state digest/trace, and can autoplay a seeded campaign. `bash tools/test-empires-endgame.sh` runs the focused unit suites, boots strict-port Vite, requires that launched process's own readiness marker and runs Cypress flows for the missing finish action, automatic empty-hand recovery, constructor clone, QA storage isolation, the three-choice gift transition, Council legibility/action, all 62 Development nodes plus editor drag and missing-position layout, event choice and no-stall autoplay (`features/empires-endgame/qa.ts`; `qa.spec.ts`; `cypress/e2e/empires-endgame.cy.ts`; `tools/test-empires-endgame.sh`).

## 13. Localization

The global RU/ENG control is visible even during login, defaults to English when `kotgh_locale` has not been saved, and persists every choice under that key. After authentication it invokes `SetLanguage` so the account and Discord surface share the preference (`App.vue` `changeLocale`; wrapper `signalr.ts` `setLanguage`). `i18n.ts` imports `characters`, `englishCatalog` and `phrases` only from `virtual:public-localization`; it no longer imports raw backend JSON into runtime code. At build/dev transform time, `publicLocalizationPlugin` reads the canonical files, retains catalog-enabled character/passive content, removes catalog records and phrase groups that contain any explicitly private authored term in any letter case, then serializes only that sanitized payload into the module. This is a packaging boundary, not gameplay masking: private owner text may arrive dynamically in the scoped DTO and falls through untranslated/verbatim, but private character/passive names, descriptions and localization variants are absent from static Store/Achievements/general bundles (`vite.config.ts` `publicLocalizationPlugin`; `i18n.ts` `catalog`/`phraseCatalog`). New `|>PhraseV2<|` records decode their embedded rendering; this includes arbitrary AI-generated Witcher clues because both texts travel inside the payload rather than entering a client dictionary. Old `|>Phrase<|` records match passive title plus exact Russian body against every public shared variant (`i18n.ts` `authoredLegacyPhrase`). The Chronicle translates its complete source before Discord markdown becomes HTML, keeping dynamic-name templates intact (`FightAnimation.vue` `formatLetopis`). Fixed UI empty states and deterministic public character lines come from the same sanitized backend-owned exact catalog; mixed Block, Rumbling, Mitsuki-total and Shock Shield records are completed without changing state keys (`i18n.ts` `phraseRules`; `i18n.spec.ts`). `MediaMessages.vue` chooses paired RU/EN DTO fields directly, including inside replays. Class labels/tooltips stay canonical in state and Russian passive/name strings remain backend dispatch keys. Details: [LOCALIZATION.md](LOCALIZATION.md).

Achievement and Daily Quest metadata are deliberate typed exceptions: both DTOs carry paired names/descriptions, and their reward components select fields directly from `currentLocale` rather than translating identifiers (`signalr.ts:636-691,744-762`; `DailyQuestBoard.vue:98-166`; `AchievementBoard.vue:73-130`; `AchievementPopup.vue:100-108`). Related Achievement character names and Daily Quest IDs remain canonical identifiers.

Generated game stories carry separate RU/EN locale containers in one artifact; the global language CSS selects the visible block (`App.vue:487-490`). The backend requests each language independently, prompts for at most 250 words / 1,700 characters without post-generation trimming, and fills a failed or configuration-disabled side with a localized unavailable message, so one API failure cannot hide the other story or produce a blank locale view (`GameStoryService.cs:65-141,448-492,637-647`). Development builds warn on Cyrillic left in an English-rendered DOM node (see `Web/VueClient/src/i18n.ts`).
