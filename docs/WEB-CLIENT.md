## 1. Stack & build

- Vue 3.5 + TypeScript + Pinia 2 + vue-router 4, SignalR client `@microsoft/signalr` 8, icons `lucide-vue-next` (package.json dependencies). Scripts: dev = vite, build = vite build, serve = vite preview, `test:99lc` / `test:empires` = focused Vitest suites, `test:99lc:e2e` / `test:empires:e2e` = Cypress browser scenarios, type-check = vue-tsc (broken in this environment — **`pnpm build` is the verifier**, per AGENTS.md), lint = eslint --fix.
- Build outputs **straight into the backend's wwwroot**: `outDir` ../../King-of-the-Garbage-Hill/wwwroot with `emptyOutDir` (`vite.config.ts:15-19`) — deploying the backend ships the SPA.
- Dev proxy forwards `/api`, `/gamehub` (ws), `/art`, `/sound` to the **production EC2 box** http://3.65.44.127 (`vite.config.ts:24-44`) — local dev talks to prod by default; a commented localhost:3535 alternative sits in the .env file. Prod build uses same-origin: .env.production sets empty VITE_API_HOST and VITE_SIGNALR_HUB=/gamehub.
- Path alias `src` → ./src (`vite.config.ts:10-14`); Vitest uses jsdom plus `src/setupTests.ts`. The focused 99LC suites cover configuration/loading validation (including spawn/hazard geometry, content references, route capacity and every equipment mode), deterministic capped generation, death/retry erosion, Chance-priced interactions and corpse-bound loot, enemy attack queuing/parries/leap target locks/boss phases, persistent basic combos, all five gesture sequences, standard/raw-Sony gamepad normalization and controller route entry. Its Cypress flow exercises route selection and the hold-follow-up attack through the browser Gamepad API boundary, plus Builder persistence versus fresh-generation application (`features/last-chances/*.spec.ts`; `cypress/e2e/last-chances.cy.ts`).
- Browser localization is assembled by the Vite `publicLocalizationPlugin`: it emits the virtual `virtual:public-localization` module from definitions whose `BrowserCatalog` is not false, then case-insensitively sanitizes exact/term/phrase catalogs against every explicitly private name, description, localization variant and passive before Rollup sees them. Content from a `BrowserCatalog: false` definition therefore does not ship in the static browser bundle; an authorized owner can still receive their own dynamic DTO text at runtime (`vite.config.ts` `publicLocalizationPlugin`; declaration `src/virtual-public-localization.d.ts`).
- Gotcha: `VITE_API_BASE` is read in two places but **never defined** in any env file — it resolves to '' so fetches stay relative (`replay.ts:11`, `Lobby.vue:9`); works only because of the proxy/same-origin setup.

## 3. Identity & session (client side)

Two login paths in `LoginProcess.vue`: a numeric **Discord User ID** input validated `/^\d+$/` with a "Copy User ID via Developer Mode" hint, or a **web username** (max 32 chars). Its buttons use the parent/store busy state and an inline ARIA alert, so a failed initial transport start re-enables a visible retry instead of leaving the login poisoned (`LoginProcess.vue:1-87`; `App.vue` `connectAndAuth`/`connectAndAuthWeb`/`handleWebLogin`). `App.vue` connects + authenticates and persists `discordId`, or lets the server mint a web account; the store saves `kotgh_web_id`/`kotgh_web_username` when `WebAccountCreated` arrives (`game.ts:317-339`). `restoreWebSession` re-authenticates from those keys (`game.ts:822-833`). There is no password — see the trust model in WEB-BACKEND.md §2.

## 4. SignalR client (`signalr.ts`)

Singleton `signalrService` (`signalr.ts:1644`); hub URL from VITE_SIGNALR_HUB, default /gamehub (`signalr.ts:3`).

- **Lifecycle**: `connect()` builds the connection `withAutomaticReconnect` at 0/1s/2s/5s/10s/30s and registers every handler (`signalr.ts:1067-1182`). A failed first start or exhausted disconnected instance is stopped and discarded so explicit login can build a fresh transport; reward invokes additionally require an authenticated session, not merely a connected socket (`signalr.ts:1053-1083,1194-1260`). **On reconnect it re-authenticates with the remembered ID and re-joins the remembered game** (`signalr.ts:1184-1195`).
- **Server events → store** (handlers assigned in `useGameStore.connect()`, `game.ts:159-382`): quest and achievement state retain their existing recovery behavior; `StoreState` replaces the full owner-only shop snapshot after reads and durable transactions, clears the matching busy/error state, and mirrors its ZBS balance into an already-loaded quest board (`game.ts:284-293`). Re-authentication refreshes the shop only after that surface has been opened once (`game.ts:341-349`).
- **Invoke wrappers** mirror the hub 1:1 (WEB-BACKEND.md §4), including Gordon's `announceHalfLife3(gameId)`, `wakeGordon(gameId)` and serial-protected `resolveHalfLife3Decision(gameId, decisionSerial, 'freeze'|'postpone')` (`signalr.ts:1472-1485`), the character-store request/adjust/reset methods, and account-level `requestDoomFortress`/`equipDoomModule`.

## 6. Stores (Pinia)

**`useGameStore`** (`game.ts:54`) — the core store.
- State refs (`game.ts:57-97`): identity/game/meta state plus quest state/loading/error/reroll ID, resumable `lootBoxResult`, store-owned loot-modal priority, achievement board/full celebration queue/loading/acknowledgement-error state, character-store snapshot/loading/action/error state, character list and `doomFortressState`.
- Getters: `myPlayer` by myPlayerId — null for spectators (`game.ts:96-103`); `opponents` (`game.ts:105-110`); `isMyTurn` = not paused, not ready and not skip, with round-8 Madara always locked false (`game.ts:118-123`); `roundTimeLeft` = turnLength − timePassed; `isInGame`, game/admin flags and character helpers. `isTerminalMode` and `myTerminalState` are generic owner-only selectors over the matching `Player` projection; components never detect this presentation by a character/passive string (`game.ts` `isTerminalMode`/`myTerminalState`).
- `connect()` (`game.ts:154-364`) wires every SignalR callback; the `GameState` handler additionally diffs own stats for sounds, **auto-joins Blackjack when newly dead to Kira**, and captures full finish-time achievement entries once per game (`game.ts:175-238`). Quest/board callbacks restore server-held Daily Quest/loot/achievement state (`game.ts:242-275`); authentication hydrates both reward families (§4).
- Action wrappers mirror the hub and layer client SFX: block plays block + Geralt meditation + turn-10 layer, levelUp records `pendingLevelUp` for sound resolution, and moral exchanges play once per round. Gordon's wrappers reject announce/wake locally during a paused transition and submit the server-supplied decision serial with the release choice (`game.ts:525-545`); the backend remains authoritative.
- Daily Quest requests expose dedicated loading/error state; one in-flight request queues at most one trailing refresh (so a call spanning UTC midnight cannot strand yesterday's board), and `rerollDailyQuest` keeps the chosen card busy until the server sends its durable replacement (`game.ts:685-717`; hub wrappers `signalr.ts:1512-1518`). Loot wrappers keep acknowledgement explicit: `openLootBox` invokes `OpenLootBoxV2`, waits at most 12 s for the server event and exposes the idempotent retry path; acknowledgement refreshes current inventory, and `clearLootBoxResult` removes only the matching result (`game.ts:719-767`; wrapper `signalr.ts:1520-1526`). Achievement dismissal snapshots the IDs shown but **keeps the popup/queue visible** while saving; only a successful selective acknowledgement removes them, while failure stays inline and retryable (`game.ts:795-827`). Logout hard-resets quest/reward/modal/ack state (`game.ts:396-444`).
- Character-store wrappers keep one account transaction in flight, expose page-local loading/errors, and rely on each returned full snapshot as the durable confirmation; requests, ±1/±10 changes, one-character refunds and refund-all live at `game.ts:815-873`.

**`useReplayStore`** (`replay.ts:122`) — replay playback. State: replayData/raw currentRound/currentPlayerIndex/currentFightIndex (`replay.ts:122-129`). The round-window adapter detects format v2 versus legacy boundary files (`replay.ts:21-54`): v2 uses actual round numbers and explicit `preFightPlayers`; legacy raw URL key K remains K for old deep links but is displayed as logical combat round K−1 and obtains pre-fight state from the preceding boundary (`replay.ts:133-166`). `computedGameState` (`replay.ts:177-269`) **reconstructs a full GameState** from the chosen round + player perspective so normal in-game components render replays unchanged: `buildShiftedPlayer` takes fight-facing actions/character/passive state from pre-fight and settled score/place/death/breakdown from the atomic result, discarding its next-round status/log buffer (`replay.ts:56-120`). V2 appends only explicit HandleLastRound personal/global suffixes (`signalr.ts:1001-1019`); legacy final files retain their inseparable raw final personal buffer (`replay.ts:48-54,165-166,208-258`). Other players' private blocks remain stripped (`replay.ts:199-240`), and replay state is finished/admin-visible (`replay.ts:243-268`). Because captured private snapshots reflect the original player's presentation locale (`ReplayService.cs:301-339`), the Vue boundary re-localizes canonical and older mixed phrase records for the current replay viewer (`Web/VueClient/src/i18n.ts:146-196`). `loadReplay` fetches the anonymous REST payload and starts on the final playable logical round (`replay.ts:273-295`). Alignment fixtures cover legacy URLs/logs, v2 numbers, skip isolation, post-setup score/death/breakdown and final personal/global settlement (`replay.spec.ts:66-223`).

**`useBattleshipStore`** (store/battleship.ts) — minigame state/lobby/placement/combat/VFX state with its own signalr callback wiring; independent of the main game store (§12).

## 7. Pages & flows

- **Fight Calculator** (`FightCalculator.vue`, route `/fight-calculator`): local-only combat lab for two teams of up to six units. Each unit can configure HP, movement speed, primary/secondary/dagger weapons, mastery, helmet/mail/padding/plate armor and talents. The seeded engine (`features/fight-calculator/engine.ts`) resolves mirrored slots, free-opponent fallback and survivor collisions while logging range, fatigue, techniques, penetration, armor/weapon degradation and status effects step by step. The baseline catalog (`features/fight-calculator/catalog.ts`) transcribes the supplied weapons-and-armor spreadsheet; the Balance dialog can edit mechanics/catalog values and add custom weapons, armor or talents. Named profiles, their balance copies and team layouts stay browser-local under `kotgh_fight_calculator_profiles_v1`; this surface has no SignalR or backend contract.
- **99 Last Chances** (`LastChances.vue`, public route `/99lc`): client-only real-time vertical slice with a seeded six-normal-tier-plus-boss run graph, room choice, isometric combat, traps, post-combat interactions, Chance-priced equipment, fixed room contents across death retries, configurable Chance loss/stat erosion, authored intro/end scenes and a built-in definition editor. It is independent of the main game store and can be opened without authentication; there are no account rewards or hidden server state in this prototype.
- **Lobby** (`Lobby.vue`): polls only `refreshLobby` every 3 s, while Daily Quests refresh on authentication/mount, visibility return and the board's UTC countdown rollover. Its persistent Rewards hub shows live ZBS, pending box inventory, Rare+ distance/base Legendary chance, the next guaranteed loot character plus remaining FIFO count, achievement completion/new badge and current-catalog totals (`Lobby.vue` reward hub). `DailyQuestBoard` renders the typed bilingual 2/3 daily + 3/3 mastery path, streak, explicitly explained 5/7 weekly journey, free reroll and all load/error/empty states; a replaced card is announced and receives focus after the old reroll button disappears (`DailyQuestBoard.vue:1-604`). The admin-only “Test New Game” button lazily requests the viewer-scoped `CharacterList`; persistent `PlayerType == 2` accounts receive the ordinary Tier ≥ 0 choices plus unknown_bug from the server, while its definition remains absent from the static bundle and regular callers receive only the unchanged public list used by achievement filters (`Lobby.vue` `openTestGamePicker`; WEB-BACKEND.md §4). The loot flow still owns modal priority and keeps its bounded retry/acknowledgement handoff unchanged (`Lobby.vue` loot flow).
- **Achievements** (`Achievements.vue` + `AchievementBoard.vue`): dedicated `/achievements` center (`router.ts:65-69`). It requests the board/character list, shows completion and reward summaries plus three nearest non-secret completions, then supports category/status/rarity filters and genuinely bilingual search across both EN/RU name, description and secret-hint pairs plus character names. Cards render character avatars, best-single-match progress, secret hints, rewards, rarity, unlock date, loading skeletons and retry/error states (`AchievementBoard.vue:22-197`; `AchievementBoard.vue:200-434`).
- **Game** (`Game.vue`, the main view): existing three-column play surface and ordinary finish flow are unchanged. For a fooled Вечное Цукуеми viewer only, the synthetic final FightLog plays before the podium/winner theme (15-second safety fallback); Madara and a Gordon who reserved Wake receive the authoritative ending without synthetic fights, while unknown_bug receives the authoritative ending with any real fight its immune action produced. `prefers-reduced-motion` bypasses both illusion waiting and the fixed five-second podium/confetti gate, and achievement popups wait for the same illusion handoff (`Game.vue` `finishPresentationPending`/`revealFinishedGame`; server projection in WEB-BACKEND.md §7). On every authenticated **non-game route**, `App.vue` hosts the same queue unless the loot flow currently owns modal priority.
- **Gordon action/transition flow**: while Halflife 3 can be announced, Gordon's ordinary Block slot becomes the one-shot `Halflife 3` action; `Проснуться` appears beside Skip only when the owner DTO says G-Man can wake him. A public transition pause forces `isMyTurn=false`, disables every inline action and attack affordance, hides `RoundTimer`, and mounts `HalfLife3Transition` in the authenticated game page. Gordon receives a non-dismissible, focus-trapped release-review dialog with the server's failure text, raw points, multiplier, exponent, final total, postponement count, exact attempt-specific button labels and deadline; every other player on that page receives the full-screen wait overlay. An expired client countdown disables both choices while the server applies the authoritative timeout freeze (`Game.vue` `gordonState`/`transitionPaused`; `HalfLife3Transition.vue`; `game.ts:118-123,525-545`).

## 12A. 99 Last Chances prototype

The `/99lc` surface is a self-contained browser prototype built on Vue plus a native Canvas 2D engine under `features/last-chances/`; it does not call REST, SignalR or the account economy. The engine renders one configured room at a time through an isometric projection and performs collision and combat on world coordinates while the run plan remains seeded and immutable. Keyboard/mouse, touch and normalized gamepad controls feed the same movement and two-hand gesture recognizers. A controller-only player can select and enter available route nodes before combat; the selected node and connected-pad state remain visible.

Each new generation creates an immutable seeded graph with six configurable normal tiers and a boss node. Every next-tier node receives an incoming edge and no parent exceeds `graph.choicesPerNode`; definitions whose available edge capacity cannot satisfy both rules are rejected. Each schema-v3 room provides at least two named spawn layouts. A node selects one layout from its seed, records its `spawnLayoutId`, and deep-copies that room's formation, hazards and interaction, so room archetype, formation, traps, offers and graph links remain stable when the player dies. Validation requires every eligible layout to hold that room's maximum enemy count, fits the player and largest eligible enemy circle inside room bounds and outside obstacles, rejects overlapping enemy circles, keeps every enemy at least the combined radii away from `playerSpawn`, bounds every hazard and validates all interaction weapon references. A retry returns to the opening choice with enemies restored while subtracting the current tier's configured Chance cost and applying the configured health, mind, attack, speed and armor erosion; a deliberately requested new generation replaces the seed, clears remembered deaths/corpse loot and restores the initial 99 Chances. Room completion exposes only connected next nodes in the route-map overlay (`plan.ts` `makeNode`/`connectTiers`; `config.ts` `validateGraphCapacity`/`validateSpawnGeometry`/`validateContentReferences`).

Each active input owns five data-defined attacks keyed by `tap`, `doubleTap`, `doubleTapHold`, `hold` and the legacy internal key `holdThenDoubleTap`. The latter means one hold/release followed by one short repeat press inside the configured follow-up window — two presses total — and is labelled “Hold + tap”. Schema v3 retains the measured press durations through resolution, permits explicitly disabled slots, selects ordered charge bands and supports channels, post-action recovery/root, per-skill invulnerability, repeat hits, true damage, cooldown refund/reset and hit statuses. An action below its first charge band remains unarmed; the spear's spin follow-up therefore exists only after its middle or late hold sector. Any authored invulnerability lasts at least through the resolved charged action duration, so a late Axe leap or Katana dance cannot become vulnerable before its movement finishes. Ordinary taps never enter the cooldown map, while per-weapon combo/rhythm state controls spear/Axe/Katana/Sword follow-ups and Claw hit parity (`features/last-chances/gestures.ts` `LastChancesGestureRecognizer`; `weapon-runtime.ts` `resolveLastChancesChargedAttack`; `engine.ts` `performAttack`/`updateHeldWeaponMechanics`).

Every attack resolves one authored sector, capsule, circle/ring or rotating sweep from `features/last-chances/colliders.ts`. The same resolved world collider performs collision and produces a fading Canvas trace. A collider may make its inner dead zone strict, rejecting an enemy whose body overlaps that protected radius; the shipped Spear uses this for real body-to-body contact rather than testing only enemy centers. Projectiles sweep their radius between frames; dashes sweep the authored forward/dead-zone capsule or moving blade, including the connector volume between consecutive blade poses; rotating areas subdivide large angular steps by their real width so low frame rate cannot leave invisible gaps. Enemy armor/dodge and reusable bleed, poison, burn, chemical, stun, disarm, healing-block, armor-break, slow, attack-slow, bind and opening states live in the runtime snapshot. Five fixed gesture colors appear both in the accessible weapon panel and as readiness pips around the player; readiness includes slot, resource, recovery and cooldown state, while held actions add a segmented in-world charge ring using the real release thresholds. The player body renders translucent for the exact invulnerability window; every authored critical outcome raises the shared world-space `CRIT` cue, and enemy status/opening/capture markers remain world-anchored (`colliders.ts` `resolveAttackCollider`/`colliderHitsCircle`/`colliderTracePath`; `statuses.ts`; `engine.ts` `dashStepColliders`/`updateActiveAreas`/`damageEnemy`/`renderColliderTrace`/`renderActionCues`/`renderPlayer`; `WeaponCooldowns.vue`).

Enemy definitions now assign `creep`, `standard`, `elite` or `boss` roles plus melee, projectile, heavy-area or leap attacks. Creeps may attack concurrently, while every non-creep shares one attack slot so surrounding enemies continue to reposition instead of striking simultaneously. ## 12B. Empire's Endgame

The `/empires-endgame` surface is a self-contained, deterministic browser game. A campaign alternates full-deck Durak against God, scoring/divine-gift resolution, an empire-planning phase and scheduled Alliance defenses (`pages/EmpiresEndgame.vue`; `features/empires-endgame/engine.ts` `EmpiresEndgameEngine`). The 53-card deck contains ranks 2 through Ace in all four suits plus the Joker/Jester. It implements legal same-rank throw-ins, same-suit/trump defence, the unbeatable configurable Joker, a pending-take window in which the attacker can finish throwing cards, attacker-first refill and role retention/swap. Engine-backed take/finish controls are invalidated on every state emission, and the runner automatically closes a resolvable attack when the player's hand is empty, so a bout cannot wait for a hidden control. The left deck is deliberately non-interactive and labelled as automatic refill; its visible bottom card is `deck[0]`, while normal draws use `pop()` from the other end (`pages/EmpiresEndgame.vue` `runGodTurns`/`trumpCardView`; `components/empires-endgame/DurakTable.vue`).

Every card definition owns editable upright and reversed forms, including its independent card name, suit/rank, time cost, value, image, passive title and effects. Cards retained between cons contribute their current-side effects; the empire receives 59 days minus those cards' time costs. `cardFlagBonuses` owns the current hand's temporary flags separately from permanent gift/event/research state, so the next con removes them without erasing permanent values; legacy empire/event snapshots reconstruct missing ownership from their held card faces. The live faces implement only mechanics whose exported numbers and current-loop substrate exist, including farm productivity, recruitment lock/bypass, military arson and famine production. An export-undefined or future-system face carries `deferredReason`: it remains an ordinary playable Durak card, but its empire effect is visibly badged as unavailable and is never applied (`types.ts` `EmpiresCardFace`/`EmpiresEmpireState`; `engine.ts` `heldCardFlagBonuses`/`recordCardFlagBonuses`/`clearCardFlagBonuses`; `components/empires-endgame/EmpireCard.vue`).

The bundled scenario currently uses three bouts per con. This remains a compatibility value rather than a resolved design verdict: `DiscordExports/empire_prompt` says a con is a configurable “several turns”, while the earlier version of this document claimed ten. The three-way question is retained at `/durak/boutsPerCon` in `EMPIRES-ENDGAME-DESIGN-REVIEW.md`; Phase 0 does not change the number. Configurable performance rules award card improvement/restoration points, then three weighted, currently executable gifts are drafted; `giftIsUnlocked` keeps relic-kind gifts out of the pool until `relicsUnlocked`. City-targeted gifts no longer advance immediately: `chooseGift` records a serialized `EmpiresPendingGiftResolution`, the target dialog lists only accessible cities, and `resolvePendingTarget` rebuilds eligibility from the trusted configuration when a save is restored before applying the result. «Ресурсы в выбранный город» and meteorite iron enter only the chosen city's ledger. The meteor targets the deterministic highest raw-level building (ID tie-break), removes its configurable `damageLevels`—one in the bundled scenario—and locks that building for the con. Region-sacrifice gifts write `destroyedRegionIds`; the region remains inspectable for history, but its cities leave every target, production, construction, recruitment, boost, population and settlement boundary. The farm/lumber relic writes typed `buildingLevelBonuses`; exact authored higher levels are used when present and `buildingLevelDefinitionAt` deterministically extrapolates the last level delta above the configured cap, so effective current level, maximum, production and worker demand agree (`types.ts` `EmpiresGiftResolution`/`EmpiresPendingGiftResolution`; `engine.ts` `beginDivineGift`/`giftIsUnlocked`/`chooseGift`/`resolvePendingTarget`/`damageCityWithMeteor`/`applyFixedGiftResolution`/`effectiveBuildingLevel`; `components/empires-endgame/TargetResolutionDialog.vue`; `EmpireMap.vue`; `CityView.vue`).

The default empire spans five regions, ten subregions and 25 configured city sites. Thirteen are initially accessible: two perimeter cities in each outer region, four Tetrakor cities and the capital. Each outer region also has three Perst-gated sites, yielding the authored five-city `2 > 2 > 1` defense topology after a permanent governor assignment. City resource stockpiles are first-class save state: local construction and recruitment spend the target ledger before the shared empire reserve. An operational Small Temple permits deterministic cross-city payment from other Small-Temple cities with the authored transfer loss; `cityAvailableResource` and `resourcePaymentPlan` are shared by the engine and availability display. Food is settled per accessible city from production, then its local food stock, then the shared empire food reserve, so selected-city food, global gifts and emergency purchases are useful without becoming a duplicate spend. Construction commitments and recruitment project the post-action workforce, production, civilian demand, army upkeep, local/shared reserves and already committed food before accepting the order (`engine.ts` `cityAvailableResource`/`resourcePaymentPlan`/`canFundFoodDemand`/`foodConsumptionForCity`/`recruitUnits`/`finishEmpireInternal`; `pages/EmpiresEndgame.vue` `cityViews`; `components/empires-endgame/CityView.vue`).

Political state is first-class rather than a family of magic flags. Each city stores base loyalty and each region stores a bounded modifier plus `controlled`/`rebellious` lifecycle state; effective city loyalty is their clamped sum. The configured −9…+9 workforce table is the only divisor reader (`−9 → ÷19`, `0 → ÷9`, `+9 → ÷1`, with every intermediate value explicit). The same effective workforce and loyalty gates feed building operation, construction projections, recruitment, production and settlement. Construction and recruitment require non-negative effective city loyalty. The Smithy additionally requires non-negative Мещане loyalty and reports that class gate separately from worker shortage. Two region-delta applications at −6 or below trigger rebellion; two at 0 or above restore normal control. Rebellion preserves cities and history but removes the region from the shared accessibility path, while `destroyedRegionIds` remains the separate permanent-loss path. Capital Forum's confirmed two-direction operational multiplier has a typed reader, but the bundled building stays deferred because “progress acceleration” has no executable meaning (`types.ts` `EmpiresLoyaltyConfig`/`EmpiresLoyaltyState`; `engine.ts` `applyLoyaltyDelta`/`effectiveCityLoyalty`/`availableWorkforce`/`updateRegionControl`/`isRegionAccessibleInState`; `components/empires-endgame/LoyaltyPanel.vue`).

Reputation is a typed clamped −9…+9 empire scalar and `reputation` is a real dependency kind; later trade/union content can consume it without making that content live early. Every loyalty/reputation mutation records source provenance in a sequence-numbered chronicle. Battle loss first records the canonical TD result identity, then applies the configured −1 city penalty only when aggregate losses attributed to that city are at least 10% of its deployed denominator. Consumed result IDs survive restore, so replay/reload cannot charge twice. Chronicle IDs are stable, projection is newest-first, and complete entries are bounded to 64 in the bundled rules. The `loyalty-rebellion` QA fixture crosses TD loss, rebellion, save/restore, recovery, a second non-destructive rebellion and retention trimming; the browser scenario exposes exact status and disabled reasons (`engine.ts` `consumeBattleLoss`/`applyReputationDelta`/`chronicleNewestFirst`; `features/empires-endgame/phase4.spec.ts`; `features/empires-endgame/qa.ts`; `cypress/e2e/empires-endgame.cy.ts`).

Seasons are derived from the current con and the ordered config cycle; no second season value is saved. The bundled reviewable cycle alternates one-con Summer and Winter. Its five damage types are ударное, дробящее, рубящее, режущее and колющее. `autoSelectDamageType` always chooses режущее for an unarmored target when the profile has it, or колющее when that concrete level is strictly greater than the target's overall armor level. Otherwise it prefers an authored type that counters the armor, then a neutral type, then one the armor counters; level and configured damage-type order break the remaining ties. `resolveDamage` returns the chosen type, selection reason, raw authored level, armor snapshot, every matched counter, passive-suppression sides and final damage. A counter suppresses all passives on the countered item. Mixed profiles cannot themselves be countered; a `twoTyped` profile checks both constituent types and can match both directions.
